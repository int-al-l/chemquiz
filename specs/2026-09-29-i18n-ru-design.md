# Russian translation (RU / EN)

Date: 2026-09-29 · Branch: `nik/i18n-ru` · Status: design approved, awaiting spec review

## Why

The site is English only. Students and teachers in Russian-speaking classes
should be able to use all of it in Russian, and a teacher should be able to
run a class game in Russian.

## Decisions

- **Everything a user sees is translated:** the interface, the cards (names,
  descriptions, aliases) and decks, server error messages, and the emails.
- **The app (cards, quizzes, profile):** each user picks RU or EN. On the first
  visit the language follows the browser (`navigator.language` starting with
  `ru` → Russian, anything else → English); the choice is then remembered on
  the device.
- **The class game:** the teacher picks the game's language when opening the
  room. The board and every phone use it; phones have no switch of their own.
- **Approach:** a small hand-written i18n module on the frontend for interface
  strings (no library); card and deck texts and error messages are localised
  by the server from the request's language.
- Current content: 110 cards in 13 decks (after PR #3, #4 by the other person).
  The Russian texts are written by Claude using established Russian laboratory
  terms ("холодильник Либиха", "колба Бунзена") and should be read by someone
  who knows chemistry before merge.

## 1. Content and server

**Russian card texts** live in a hand-edited file, `backend/content_ru.py`:

```python
ITEMS = {
    "liebig-condenser": {
        "name": "Холодильник Либиха",
        "description": "…",
        "aliases": ["прямой холодильник"],
    },
    ...
}
CATEGORIES = {"condensers": {"name": "Холодильники", "description": "…"}, ...}
```

Not in `seed_data.py`: that file is regenerated by `catalog/synthware/build.py`
and conflicts badly. `content_ru.py` is never regenerated and the photo pipeline
does not touch it. New cards get a new entry here.

**Database.** `Item` gains `name_ru`, `description_ru`; `Category` gains
`name_ru`, `description_ru`; `ItemAlias` gains `lang` (`"en"` default, `"ru"`).
`migrate.py` adds the columns to existing databases; `seeding.py` fills them
from `content_ru.py` (a card missing from it simply has NULL Russian fields).

**The request's language** — `app/i18n.py`:

1. in a live game, the game's `lang` (the header is ignored);
2. otherwise `Accept-Language` — the frontend sets it from the user's choice;
   a value starting with `ru` → `"ru"`;
3. otherwise English.

`localized(obj, field, lang)` returns the Russian field when `lang == "ru"` and
it is set, otherwise the English one — so a missing translation shows English,
never a blank. Every payload with card or deck text (`crud.item_payload`,
`category_payload`, quiz questions and results) takes the language.

**Error messages.** All user-facing messages (about 38) move into
`app/messages.py`: `{"game_not_found": {"en": "No game with that PIN", "ru": "Игры с таким PIN нет"}, ...}`.
`LiveError` and the routers' `HTTPException`s carry a message key; the error
body stays `{"detail": "<text in the request's language>"}` and gains
`"code": "<key>"`. Messages with values (`Names can be at most {n} characters`)
use `str.format`.

**Emails.** Verification and reset emails are written in the language of the
request that sends them (register, resend, forgot).

**Live game.** `live_games` gains `lang` (`"en"`/`"ru"`, default `"en"`).
`POST /api/live` accepts `lang`. Questions are frozen at creation, so they are
drawn in the game's language, and history shows a game in the language it was
played in. "Play again" (both kinds) keeps the old game's language. Host and
player views, and `GET /api/live/{pin}`, include `lang`. Errors on live
endpoints are in the game's language when the game is known.

## 2. Frontend

**`src/i18n/`:**

- `en.js`, `ru.js` — flat dictionaries: `"quiz.next": "Next"` / `"Далее"`.
- `LanguageProvider` — holds the language: `localStorage` (`chemquiz.lang`) →
  otherwise `navigator.language` → otherwise `en`. It tells `api/client.js`,
  which sends `Accept-Language` with every request, and sets `<html lang>`.
- `useT()` → `t(key, values)`: `{n}`-style substitution, plurals through
  `Intl.PluralRules` (`"live.players": {one: "{n} игрок", few: "{n} игрока", many: "{n} игроков"}`);
  a missing key falls back to English, then to the key itself.
- `useLang()` → `[lang, setLang]`; dates via `toLocaleString(lang)`.

**Translated:** all screens and components, level titles, badges (by `id`) from
`progress/engine.js`, mode labels, the frontend's own messages ("Could not
reach the server…").

**The RU/EN switch** is on the main menu and in the profile. Switching redraws
at once and re-fetches server data in the new language (the language is part
of `useApi`'s key). Progress and "My list" are keyed by slug, so nothing is lost.

**Live game:** the setup screen has "Game language" (default: the teacher's
language). The board and phones render in `state.lang`; the join screen starts
in the phone's language and switches to the game's once `GET /api/live/{pin}`
answers. The history screens use the user's language; CSV question headers stay
in the game's language (frozen with the questions).

## 3. Demo, tests, order of work

**Demo (GitHub Pages).** `tools/make_demo_data.py` adds the Russian fields from
`content_ru.py` to `data.json`; `src/demo/backend.js` returns card texts in the
request's language and translates its errors by the same codes. `data.json` and
`docs/` are rebuilt by CI after merge, never committed by hand.

**Tests.**

- Backend: `content_ru.py` covers every card and deck in `seed_data.py` (name
  and description); `Accept-Language: ru` → Russian texts, none / `de` →
  English; a `lang=ru` game gives Russian questions and errors whatever the
  phone's header; replay keeps the language; the email follows the request's
  language; every key in `messages.py` has both languages.
- Frontend: `en` and `ru` have the same keys; plurals for 1, 2, 5, 11, 21, 22,
  25; default language from the browser and remembered choice; existing tests
  pass.
- Manual: switch language on cards and in a quiz; a Russian class game from a
  board and two "phones".

**Order of work.** Branch `nik/i18n-ru`, draft PR with this plan early (it
touches almost every screen). Three stages, each in its own commits:

1. Server: request language, columns, `content_ru.py` (110 cards, 13 decks),
   messages, emails, `lang` on live games.
2. Frontend: `i18n` module, every screen, the switch, the game's language.
3. Demo and README.

**Risk.** Nearly every JSX file changes; parallel edits to screens by the
other person would conflict. Say so in the PR. New cards added later without
a `content_ru.py` entry fail the coverage test in CI and show English on the
site until translated.
